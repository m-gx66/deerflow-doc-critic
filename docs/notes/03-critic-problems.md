# Critic 机制：问题与观察

## 审查文档方式

来源：`df/critic机制/df_problem/审查文档方式.md`

**第一，prompt 里明确写“文档”。** 把输入描述从“回答或代码”改成“回答、文档或代码”，并单独说明文档怎么审
system_prompt: |
  你是“需求符合性审查”子 agent，不是通用代码审查员。
  你会收到两部分输入：
  1. 用户的原始需求
  2. 系统生成的产出（回答、文档或代码）

  审查规则：
  - 如果产出是文档（docx/pdf/markdown/网页等），审查文档的文字内容、结构、事实准确性和是否满足需求。
  - 不要审查“生成文档的代码”，除非用户明确要求审查代码。
  - 如果只拿到文件路径，先用可用工具读取或转换文件；读不到就明确说明“无法审查”，不要臆测内容。
  - 逐条对照原始需求，输出结论（通过/不通过）+ 问题列表 + 修改建议。

**第二，编排层保证传进去的是文字。** 最稳的做法是让 doc-processor 在产出文件的同时，返回一份 Markdown 文本（或把文件转成 Markdown 存到工作区），critic 读这份文本。如果只给它一个 `.docx` 路径，而它没有解析工具，它就只能说“读不了”，审查等于没做。

双栏排版。学术论文、技术白皮书基本都是两栏，通用转换器（markitdown 这一类）按文本流顺序抽，经常把左栏下半段和右栏上半段交错拼在一起。critic 读到的是语义断裂的段落，它会认真地批评“此处论证跳跃”“前后文不衔接”——这些全是转换引入的假阳性。你正在搭的那个 50 条评测集里，如果混进这种样本，召回率数字会被污染，而且很难事后区分是文档真有问题还是解析有问题

不会因为rag的检索太多上下文而被污染 doc与critic不带记忆

## 召回率

来源：`df/critic机制/df_problem/召回率.md`

召回率 = critic 找出的真实问题数 / 全部真实问题数

这是最需要它的场景，因为我审自己的草稿，等于让同一套推理逻辑自查，容易顺着原有的思路把漏洞也读成合理。让另一个 context 从零读草稿，才可能发现“这里其实没写清楚”。

## critic problem

来源：`df/critic机制/df_problem/critic problem.md`

leader <-> critic agent 评审循环（死循环）：critic一直判定结果为不合格，leader一直修改，来回迭代，永远达不到收敛条件，无限循环，达到1000次上限

工具调用循环：agent反复调用一个工具，没有终止判断

无法解析docx文件 ，因为是二进制文件，read_flie无法读取

返回的意见没有 JSON、没有 `verdict`、没有严重程度、没有锚点要求 都是以自由文本形式，使得评审效果不佳 **这些操作是为了让召回率更可测量** 降低ai的幻觉式意见

如何编排使得召回率提高

## doc拿到critic的意见依旧执行分析

来源：`df/critic机制/df_problem/doc拿到critic的意见依旧执行分析.md`

而这一轮暴露的正是这个薄弱环节。c1 那条误报的后果不只是多一条错误 issue，而是会让第 4 步必然无法收敛：doc 收到“把 target 改成 analysis 自己的哈希”，照做就是在文件内容里写自己的哈希，写进去哈希就变了，于是永远对不上，下一轮 critic 还会再报同一条。格式完全通畅，语义没有对齐，“格式化输出”在冲突中就失去了作用。

相当于doc收到critic的意见输出之后仍旧在执行分析操作，相当于对意见一直在分析未进行改进式输出
